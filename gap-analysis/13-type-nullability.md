# type & nullability — gap analysis

## Scope (specs covered, one line each)

- `specs/json-schema/features/type.md` — the seven type tokens, the number/integer model, the ±(2^53−1) cap, the load-time rejects (array `type`, typeless leaf, shapeless object, standalone `null`), and the P12 serialize-side re-checks.
- `specs/json-schema/nullability.md` — the optional-vs-nullable matrix (P8/P9), the four legal combinations, the per-language emitted types, the serialize omit-vs-`null` table, the strict optional-non-nullable `null` reject, and the bounded Go/Java/Python optional+nullable collapse (P1 exception (a)).
- `specs/json-schema/PRINCIPLES.md` — P1, P6-P13, TypeScript §1-4, Python §1-3, Java §1/§3-6, Go §1 as the shared base both specs cite.

## Summary

- **The loader is in good shape.** Every `type` reject the spec mandates is implemented and (mostly) tested: array form, standalone `type:"null"`, unknown name, shapeless `object`, missing `type` on a leaf, `nullable: true` (OAS 3.0), non-exact null branch, duplicate null branches. Nullability pattern recognition (2 branches, exactly-`{"type":"null"}`, order-insensitive) is correct.
- **The emitters are where this group falls apart, and it is all one root cause:** three of the four backends unwrap the nullability `oneOf` wrapper before reading a property's shape; **Go's parse dispatcher and Java's field planner do not.**
- **P0 (Go): a nullable `integer`/`number`/`boolean`/`array` property emits `parseStringField`** and assigns a `string` into a `*int64`/`*float64`/`*bool`/`[]T` field. The generated Go **does not compile** — reproduced with `go vet`.
- **P0 (Go + Java): every constraint on the non-null branch is silently dropped** — `minLength`, `maxLength`, `pattern`, non-temporal `format`, `enum`, `const`, `minimum`/`maximum`/`multipleOf` — in both directions. TS and Python enforce them. That is a direct P1 accepted-value-set divergence, and the spec's own example (`{"oneOf":[{"type":"string","format":"email","minLength":5},{"type":"null"}]}`) is exactly the broken case.
- **P0: the serialize-side integer cap (type.md §Serialize-side, P12 layer 2) exists only in Go.** TypeScript, Python and Java emit an over-cap integer without complaint; every language's parser then rejects the payload they produced.
- **P0/P1: the accepted integer set diverges near the cap.** Go parses the decimal text exactly and rejects `4503599627370496.5`; TS (`Number.isSafeInteger`), Python (`float.is_integer()`) and Java (`node.doubleValue()`) all see the already-rounded double and accept it. Java's `specLong` also diverges from the `BigDecimal.decimalValue()` helper the spec prints verbatim.
- **Nullable non-string properties are generated by exactly one test in the whole repo** (`tests/generate_python.rs:557`). Go/TS/Java presence matrices are string-only — which is precisely why the two P0s above survive.
- **The presence matrix itself is well covered in Go and TypeScript** (`go_json_wave3_pairwise_runtime_matrix`, `typescript_json_wave3_pairwise_runtime_matrix`), partially in Python, and **not at all in Java** — Java has no test for explicit-`null`-on-optional-non-nullable, no test for absent required+nullable, and no test for the collapse it documents.
- **The documented optional+nullable collapse is asserted only in Python.** Go and Java both switch to decode-only helpers at exactly the fixtures that would show it (`showcase-nulls.json`, `message-full.json`) and never re-encode. Java even has a test named `optionalNullableNullsAreOmitted` that never inspects the serialized form.
- **The conformance manifest is bookkeeping, not behavior.** `tests/json_schema_conformance_manifest.rs` only checks the manifest's own shape and that each consumer file contains an anchor substring; `permitted_presence_nullability_collapse` is never executed or verified.
- Integer spelling/cap fixtures (`1`, `1.0`, `1e2`, ±(2^53−1), `2^53`, `2^53+1`, `1.5`, `true`, `"1"`) — the spec says "identical fixture set in all four" — exist **only for Go**. TypeScript has *no* runtime integer-semantics test at all.

## Implementation divergences

### 1. Go emits `parseStringField` for every nullable non-string scalar/array property — the generated Go does not compile

- **Severity** P0
- **Spec cite** `nullability.md:231-238` (optional+nullable table: `integer`→`*int64`, `number`→`*float64`, `boolean`→`*bool`, `array`→`[]T`) and `nullability.md:245-252` (required+nullable); `type.md:111-119` (validator mapping per token).
- **Code cite** `src/generator/json_schema/go.rs:3301-3311` — the trailing `if allows_null(property) { … parseStringField … }` arm of `render_property_unmarshal`. Every preceding arm dispatches on `property.ty` (`go.rs:3153` string, `go.rs:3201` integer, `go.rs:3223` number, `go.rs:3245` boolean, `go.rs:3268` array), and `property.ty` is `None` for a nullability `oneOf` wrapper, so a nullable non-string property falls through to the string arm unconditionally. Contrast `go.rs:5271-5282` / `go.rs:5287-5299`, where `temporal_kind`/`content_encoding_kind` *do* unwrap via `nullable_non_null_schema`, which is why nullable `format: date-time` and nullable `contentEncoding: base64` work.
- **What the spec requires** A nullable integer field is `*int64` and is parsed through the integer path (`parseIntegerField` → `parseSpecInteger`), accepting `null`.
- **What the code does** Emits `if v, ok := parseStringField(get("optNullInt"), "optNullInt", false, true, &errs); ok { m.OptNullInt = &v }` where `OptNullInt` is `*int64`.
- **Concrete failing input**
  ```yaml
  type: object
  properties:
    optNullInt: { oneOf: [{ type: integer }, { type: "null" }] }
  ```
  `nexgen go` succeeds; `go vet` on the output: `cannot use &v (value of type *string) as *int64 value in assignment`. Same for `number`, `boolean`, and a nullable `array` (`m.OptNullArr = &v` into `[]string`).
- **Confidence** Certain — generated and compiled.

### 2. Go and Java silently drop every constraint declared on the non-null branch

- **Severity** P0
- **Spec cite** `nullability.md:177-187` — "The non-null branch is a full subschema and may carry any sibling keyword recognized for that `type`", with the worked example `{"oneOf":[{"type":"string","format":"email","minLength":5},{"type":"null"}]}`. P1 (`PRINCIPLES.md:14`) makes the accepted/rejected value set the non-negotiable cross-language contract.
- **Code cite**
  - Go parse: `src/generator/json_schema/go.rs:3301-3311` — the fallback emits no `render_go_string_checks` / `render_go_pattern_check` / `render_go_format_check` / closed-value check.
  - Go serialize + shared `Validate`: `src/generator/json_schema/go.rs:2720-2810` — `render_validate` gates the closed-value, integer-cap, finite-number, numeric-bound and string-constraint blocks on `property.ty == Some("integer"|"number"|"string")` and never calls `nullable_non_null_schema`. Tellingly, `go.rs:325-332` (`render_go_string_vars`) *does* unwrap, so the compiled `pattern`/`format` regex vars are emitted and then never referenced.
  - Java: `src/generator/json_schema/java.rs:1899-1968` (`resolve_model_kind`) reads `property.const_value` / `property.enum_values` (`:1899-1905`), `NumericConstraints::from_schema(property)` (`:1962`), `StringLengthConstraints::from_schema(property)` (`:1963`), `ArrayConstraints::from_schema(property)` (`:1964`) and `schema: property.clone()` (`:1965`) from the **wrapper**. Compare `java.rs:1885-1887`, which unwraps with `nullable_non_null_schema` for `additionalProperties` — the asymmetry is the bug.
- **What the spec requires** `{"nullName":"A"}` must be rejected in all four languages (`minLength: 3`, `pattern: ^[a-z]+$`); `{"nullEnum":"zzz"}` must be rejected in all four; a nullable `enum` must emit the closed type (P13.1).
- **What the code does** TypeScript and Python emit all of the checks and (for `enum`) the closed type (`"a" | "b"` / `Literal["a","b"]`). Go emits an empty `Validate()` and an unconstrained `parseStringField`; Java emits a bare `field.isTextual()` check and a plain `String` field.
- **Concrete failing input**
  ```yaml
  type: object
  properties:
    nullName:  { oneOf: [{ type: string, minLength: 3, pattern: "^[a-z]+$" }, { type: "null" }] }
    nullEnum:  { oneOf: [{ type: string, enum: [a, b] }, { type: "null" }] }
    nullEmail: { oneOf: [{ type: string, format: email }, { type: "null" }] }
    nullInt:   { oneOf: [{ type: integer, minimum: 1, maximum: 10 }, { type: "null" }] }
  ```
  `{"nullName":"A","nullEnum":"zzz","nullEmail":"nope","nullInt":99}` → TypeScript and Python raise five violations; Java accepts the whole payload. (Go does not compile at all, per divergence 1.)
- **Confidence** Certain for Java — generated and read the emitted `Deserializer`/`Serializer`. Certain for Go's `Validate` (empty).

### 3. The serialize-side ±(2^53−1) integer cap exists only in Go

- **Severity** P0
- **Spec cite** `type.md:222-233` — "**`integer` cap.** The in-memory `int64`/`long`/`int`/`number` is re-checked against `±(2^53−1)`; a value constructed past the cap is a `ValidationError`, not silently emitted. Go `int64` / Java `long` hold magnitudes the cap forbids, and Python ints are unbounded, so this check has real teeth on the out-path." Also `PRINCIPLES.md:40` (P12 layer 2 names "the integer cap" as a shared-`Validate` predicate) and `PRINCIPLES.md:42` ("Serialize runs the shared `Validate` before emitting a byte").
- **Code cite**
  - Go (correct): `src/generator/json_schema/go.rs:2729-2751` (property-level cap in `Validate`) and `go.rs:4570-4586` (map-member / union-variant cap).
  - TypeScript: no cap emission anywhere — `rg 'integer cap|MAX_SAFE|9007199254740991' src/generator/json_schema/typescript.rs` finds only `Number.isSafeInteger` on the **parse** side (`typescript.rs:3497`, `:2555`, `:785`). Generated `toTransferType` is `out.n = value.n;`.
  - Python: the cap lives only in `_parse_spec_integer` (`src/generator/json_schema/python.rs:4853-4875`) and in the union branch selector (`python.rs:2442`, `:2467`). Generated `to_transfer_type` is `out["n"] = value.n`.
  - Java: the cap lives only in `SpecNumbers.specLong` (`src/generator/json_schema/java.rs:5445-5448`). The nested `Serializer` emits `gen.writeNumberField("n", value.n);` with no preceding check.
- **What the spec requires** Constructing a model with `n = 1 << 60` and serializing must throw the aggregating validation error in all four languages.
- **What the code does** Go returns `*ValidationError{"n": "exceeds ±(2^53-1) integer cap"}`; TypeScript, Python and Java emit `1152921504606846976` onto the wire — a payload that **every** language's parser (including their own) then rejects.
- **Concrete failing input** Schema `{type: object, required: [n], properties: {n: {type: integer}}}`; native value `n = 1152921504606846976`.
- **Confidence** Certain — generated all four backends for the same schema and read the emitted serializers.

### 4. Fractional integer literals near the cap: Go rejects, TypeScript / Python / Java accept

- **Severity** P0 (narrow numeric band, but a silent cross-language accept/reject divergence — P1 says the value set is never excepted)
- **Spec cite** `type.md:15-17` ("`integer` … matches any JSON number whose fractional part is zero"), `type.md:283-293` ("reject `1.5` … Same accept/reject set in all four languages"), `type.md:189-204` (the printed `specLong` using `BigDecimal d = n.decimalValue(); if (d.stripTrailingZeros().scale() > 0) reject`), `type.md:149-156` (the claim that `Number.isSafeInteger` is "a complete and sound check").
- **Code cite**
  - Go (correct): `src/generator/json_schema/go.rs:1523-1531` — `parseSpecInteger` splits the `json.Number` **text** into digits/fraction/exponent, so a nonzero fractional digit is rejected regardless of magnitude.
  - TypeScript: `src/generator/json_schema/typescript.rs:3497` — `typeof v !== 'number' || !Number.isSafeInteger(v)`, run over the value `JSON.parse` already rounded.
  - Python: `src/generator/json_schema/python.rs:4864` — `if isinstance(value, float): if not value.is_integer(): reject`, over the already-rounded `float`.
  - Java: `src/generator/json_schema/java.rs:5440-5443` — `double value = node.doubleValue(); if (… || value != Math.floor(value)) reject`. This is **not** the `decimalValue()`/`BigDecimal` helper the spec prints.
- **What the spec requires** `4503599627370496.5` has a nonzero fractional part → reject in all four.
- **What the code does** Verified: `JSON.parse("9007199254740991.1") === 9007199254740991` (accepted); `json.loads("9007199254740991.1").is_integer() is True` (accepted); Java's `doubleValue()` does the same. Go rejects — and `tests/generate_go.rs:1998` explicitly asserts that rejection, so the Go test suite currently pins a behavior the other three violate.
- **Concrete failing input** `{"count": 4503599627370496.5}` (or `9007199254740990.5`, `9007199254740991.1`).
- **Confidence** Certain for Go/TS/Python (executed `node` and `python3` against the emitted predicates). High for Java (read the emitted `SpecNumbers.specLong`; not executed on a JVM). Note this is *also* a spec bug: the "complete and sound" claim for `Number.isSafeInteger` is false for fractional literals ≥ 2^52.

### 5. Python preserves a wire `int` in a `type: number` field, so integers past 2^53 round-trip to a different value than in Go/TS/Java

- **Severity** P1
- **Spec cite** `type.md:98-104` ("`number` is the finite IEEE-754 binary64 domain **shared by all four targets**"); `PRINCIPLES.md:14` (P1: "a value one accepts must round-trip through any other with the **same JSON value**"). `type.md:164-167` blesses "stored exactly as it arrived" but argues only about the re-emitted *lexeme*.
- **Code cite** `src/generator/json_schema/python.rs` number parse — the emitted body is `if not (not isinstance(x, bool) and isinstance(x, (int, float))): reject else: field = x` (no `float()` coercion); the finiteness guard is an exact comparison against `±1.7976931348623157e308`, which also accepts an unbounded `int`.
- **What the spec requires** The same mathematical value out of every target.
- **What the code does** `{"score": 9007199254740993}` → Python holds the exact `int` and re-emits `9007199254740993`; Go/TypeScript/Java hold a `float64`/`number`/`double` and re-emit `9007199254740992`.
- **Confidence** High — read the emitted converter and confirmed CPython's `json.loads` integer semantics; not executed end-to-end through the data converter.

### 6. Go emits `*[]T` for a required+nullable array instead of the prescribed `[]T`

- **Severity** P1
- **Spec cite** `nullability.md:252` — required+nullable `"array"` → Go `[]T` (nil = null).
- **Code cite** Reproduced from `oneOf: [{type: array, items: {type: string}}, {type: "null"}]` in `required`: `ReqNullArr *[]string \`json:"reqNullArr"\``. (Optional+nullable correctly yields `[]string`.) The type choice sits in the Go type-annotation path; the parse path for this field is separately broken by divergence 1.
- **Confidence** Certain — generated.

### 7. A malformed non-string `type` is diagnosed as "missing", and is not diagnosed at all next to a `oneOf`/`$ref`

- **Severity** P2
- **Spec cite** `type.md:258-270` — "Loader must produce a clear, located diagnostic for each", row "Wrong outer type | `5`, `null`, `true`, `{"type":"string"}`".
- **Code cite** `src/parser/json_schema.rs:1653-1658` — `validate_type_presence` does `schema.ty.as_ref().and_then(Value::as_str)` and, on `None`, reports "a leaf schema requires an explicit `type`". `src/parser/json_schema.rs:1641-1643` returns `Ok(())` early whenever `reference` or `one_of` is set, so `{oneOf: […], type: 5}` is accepted with a nonsense `type` in the tree.
- **What the code does** Still rejects the leaf case (good), with a misleading message; accepts the combinator case.
- **Confidence** Certain (read); the combinator case is unverified end-to-end.

### 8. Spec drift — `patternProperties` listed as a way to give `type: object` a shape

- **Severity** P2
- **Spec cite** `type.md:58-61` and `type.md:266`.
- **Code cite** `src/parser/json_schema.rs:1594` — `patternProperties` is in the unconditional unsupported-keyword list; the emitted diagnostic at `json_schema.rs:1670-1672` correctly names only `properties`, `additionalProperties: true`, `additionalProperties: false`. The spec should drop the `patternProperties` mention.

### 9. Spec drift — nullability.md describes the Java serialize mechanism as `@JsonInclude`

- **Severity** P2
- **Spec cite** `nullability.md:356-358` ("`@JsonInclude(NON_NULL)` on optional fields; `@JsonInclude(ALWAYS)` forces the required+nullable `null`").
- **Code cite** The generated POJO carries no `@JsonInclude`; the nested `Serializer` writes fields explicitly (`if (value.x != null) gen.writeNumberField(...) else gen.writeNullField(...)`). `PRINCIPLES.md:84` (Java §6) already says "honoring per-field `@JsonInclude` semantics **in code**" — nullability.md should match. Behavior is correct.

### 10. TypeScript emits `null | T` when the null branch is authored first

- **Severity** P2
- **Spec cite** `nullability.md:231-252` — every table cell is `T | null`.
- **Code cite** Reproduced: `oneOf: [{type: "null"}, {type: string}]` → `a?: null | string`. Semantically identical; only the declaration reads inconsistently. Go/Python/Java are order-insensitive and unaffected.

## Testing gaps

### 1. No test anywhere generates a nullable non-`string` scalar or array for Go, TypeScript or Java
- **Severity** P0 (this is the reason divergences 1 and 2 exist)
- **Untested** `oneOf:[{type:integer},{type:"null"}]`, `…number…`, `…boolean…`, `…array…` as a *property* (element and `$ref` positions are covered).
- **Spec line** `nullability.md:231-252` — the two per-language tables have a row for every type token.
- **Where** Extend `GO_WAVE3_MATRIX_SCHEMA` (`tests/generate_go.rs:112`), `TYPESCRIPT_WAVE3_MATRIX_SCHEMA` (`tests/generate_typescript.rs:265`), a new Java equivalent, and add the same fields to `samples/schemas/showcase.nexusrpc.yaml`.
- **Suggested case** Add `nullableInteger`, `nullableNumber`, `nullableBoolean`, `nullableList` (each `oneOf:[{T},{null}]`), once optional and once required; assert parse of absent / `null` / value and the serialize form in all four.

### 2. No test declares a constraint on a nullability `oneOf`'s non-null branch
- **Severity** P0
- **Untested** `minLength`/`maxLength`/`pattern`/`format`/`enum`/`const`/`minimum`/`maximum`/`multipleOf` on the non-null branch.
- **Spec line** `nullability.md:177-187` (the `format: email, minLength: 5` example is verbatim in the spec).
- **Where** Same four matrix schemas + `showcase.nexusrpc.yaml`; also a Rust rendering assertion in each `tests/generate_*.rs`.
- **Suggested case** `nullableCode: {oneOf: [{type: string, minLength: 3, pattern: "^[a-z]+$"}, {type: "null"}]}` — assert `{"nullableCode":"A"}` yields two violations in all four, and `null`/absent yield none.

### 3. Serialize-side integer cap is untested in TypeScript, Python and Java
- **Severity** P0
- **Untested** Constructing a model with an over-cap integer and serializing.
- **Spec line** `type.md:228-233`.
- **Where** `samples/typescript/tests/json-schema-showcase.test.ts`, `samples/python/tests/test_showcase.py`, `samples/java/src/test/java/jsonschema/JsonSchemaShowcaseRoundTripTest.java`; and as a new conformance case with a `serialize_failures` entry.
- **Suggested case** `showcase.count = 2**60` (Python) / `1L << 60` (Java) / `2 ** 60` (TS) → expect one violation at path `count`. Go already has the analogous coverage through `Validate`.

### 4. The integer spelling / cap fixture set exists only for Go
- **Severity** P1
- **Untested** TypeScript has **no** runtime integer-semantics test at all. Java asserts only `1.5` (`samples/java/.../JsonSchemaRoundTripTest.java:189-196`). Python covers `3.0`, `True`, `1.5`, `2**53` (`samples/python/tests/test_showcase.py:325-337`) but not `1e2`, not the accept boundary `±(2^53−1)`, not the string `"1"`.
- **Spec line** `type.md:283-293` — "each language's helper … must pass an **identical fixture set**".
- **Where** Best as a new conformance manifest case driven from `samples/conformance/json-schema.json`, with one consumer per language.
- **Suggested case** Accept `1`, `1.0`, `1e2`, `-0`, `9007199254740991`, `-9007199254740991`; reject `1.5`, `true`, `false`, `"1"`, `"abc"`, `9007199254740992`, `9007199254740993`, `18014398509481985`. Add `4503599627370496.5` once divergence 4 is fixed.

### 5. Non-finite / overflowing number tokens are untested on the parse side
- **Severity** P1
- **Untested** `1e400` (overflows to infinity → must reject) in all four languages; `1e-400` (underflows to 0 → must accept, and does in all four — verified for Go's `strconv.ParseFloat`).
- **Spec line** `type.md:98-101` — "A numeric token whose correctly rounded value overflows to infinity (for example `1e400`) is rejected."
- **Where** Add to the `mathematical-number-equality` conformance case as a `parse_failures` entry.
- **Suggested case** `{"score": 1e400}` → one violation at `score`; `{"score": 1e-400}` → accepted as `0`.

### 6. The optional+nullable collapse is not asserted in Go or Java
- **Severity** P1
- **Untested** wire `middleName: null` → re-serialized output omits the key. Both suites deliberately switch to decode-only at exactly that fixture: `samples/go/tests/json_schema_showcase_test.go:70` (`decodeFixture`) and `samples/java/.../JsonSchemaShowcaseRoundTripTest.java:137` (`decode`). Java's `JsonSchemaTemporalRoundTripTest.optionalNullableNullsAreOmitted` asserts only `assertNull(getDeletedAt())` and never inspects the output bytes.

## Verified-good

- **Loader `type` handling.** `validate_type_form` (`json_schema.rs:1764-1784`) rejects the array form and standalone `type: "null"` with the fix-it the spec prescribes, and correctly exempts a union branch; `validate_type_presence` (`json_schema.rs:1641-1691`) rejects a typeless leaf, an unknown token, a shapeless `type: object`, an `items`-less `type: array`, and `properties`/`items` on the wrong token, while exempting `oneOf`/`$ref`/(merged) `allOf`. All have inline tests (`:9145`, `:9152`, `:11768`, `:11777`, `:11783`, `:11789`, `:11974`, `:11980`).
- **`nullable: true` (OAS 3.0) rejection** with the `oneOf` fix-it — `json_schema.rs:1520` + test `:9140`.
- **Nullability pattern acceptance.** Exactly-two-branch check, "null branch must be exactly `{type:"null"}`" (`json_schema.rs:4232-4243`, tested `:9176` across five sibling keywords), duplicate-null rejection (`:4272-4288`, tested `:10700`), order insensitivity (works, untested).
- **TypeScript is correct across the whole optional×nullable matrix** including the non-`string` tokens and constraints on the non-null branch, and it is the only target that preserves the wire `null` on an optional+nullable field — exactly as P1 exception (a) requires.
- **Python is correct across the whole matrix** and has by far the strongest test coverage (`test_showcase.py:190 test_nullability_states`, `test_chat.py:52-66`, byte-level collapse enforcement in `test_wire_fixtures.py:130-142`).
- **Java's four-way presence branch is structurally right** (`java.rs:3756-3791`): node-absent → `required`, `isNull()` → `explicit null not allowed` unless nullable, otherwise the strict helper — the same three-way Go uses. Emitted types match the spec (`long`/`double`/`boolean` for required non-nullable, `@Nullable Long`/`Double`/`Boolean` otherwise, `@Nullable` on every optional reference).
- **Go's struct-tag / pointer conventions match the spec exactly** for scalars: required non-nullable `int64`, optional `*int64,omitempty`, required+nullable `*int64` **without** `omitempty` (so `nil` serializes to `null`), optional arrays as nil-slices.
- **Nullable `$ref`, nullable inline object, and nullable array *elements* all work in Go** (`*Child`, `*G2NullObj`, `[]*int64` with per-element `null` → `nil`), and nullable temporal `format` / `contentEncoding` work in Go and Java because `temporal_kind`/`content_encoding_kind` unwrap the wrapper (`go.rs:5271`, `go.rs:5287`).
- **Parse-side integer cap is enforced in all four** — `parseSpecInteger` (`go.rs:1523`), `Number.isSafeInteger` (`typescript.rs:3497`), `_parse_spec_integer` (`python.rs:4853`), `SpecNumbers.specLong` (`java.rs:5437`) — and `9007199254740993` is correctly rejected by all four.
- **`bool` is excluded from Python's integer and number checks** (`python.rs:4862`, and the emitted `not isinstance(x, bool) and isinstance(x, (int, float))` for `number`), so `True` is never `1`.
- **Number finiteness on serialize is implemented in all four and recursively** — properties, union branches, array elements at every depth, typed-map members — and is the one part of this group with a real cross-language conformance case (`recursive-collections`, with all four consumers wired up).
- **Mathematical-number equality** (`-0.0`, `5e0`, `1e3`, DBL_MAX, the smallest subnormal) round-trips identically in all four, covered by the `mathematical-number-equality` conformance case and per-language assertions.
- **Reason-text divergence for required-non-nullable explicit `null`** (Go/Java say `explicit null not allowed`, TS/Python say `required`) is *not* a violation — P11 explicitly excludes reason text from the contract, and the violation count and path agree.
